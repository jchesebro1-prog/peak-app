# Peak as a Native App — the Capacitor Path

**Date:** 2026-07-21
**Status:** Feasibility spec for a decision — **NOT approved, no code.** Prompted by
punch-list **#30** (Bluetooth laser in the site survey) and **#31** (native-app feasibility).
**Scope:** Wrap the *existing* Next.js PWA in a Capacitor native shell for iOS + Android — to gain
App Store / Play Store presence and native device APIs (Bluetooth first) — **without rewriting the
app.**

## TL;DR / recommendation

- **Feasible, moderate cost, reuses ~all the code.** This is a wrapper, not a rewrite.
- **Recommended model:** *remote/hybrid* — the native shell loads the hosted Vercel app; native
  plugins (Bluetooth) bridge in; the existing offline sync engine stays as-is.
- **Recommended trigger:** do it when a native capability justifies it. The **Bluetooth laser (#30)
  is that trigger** — it is the one thing the web app cannot do on iPhone/iPad. #30 and "make it a
  real app" are effectively the same decision.
- **Do NOT** do a React Native / Swift-Kotlin rewrite. Overkill for a business/field CRM.

## Current state (verified 2026-07-21)

| Fact | Value | Why it matters |
|------|-------|----------------|
| Framework | Next.js 16.2, React 19 | Modern; App Router uses **server components + server actions** |
| Hosting | Vercel (`peak-app-six.vercel.app`) | The app **needs a running server** — it is not a static bundle |
| PWA | `public/manifest.webmanifest` (linked `src/app/layout.tsx:22`), `public/sw.js`, `public/icon.svg` | Already ~80% of "an app" — installable, offline-capable |
| Offline | Sync engine in `src/lib/sync/` (`SyncProvider`, service worker, `syncState`) | Field-ready; carries data across connectivity gaps |
| Native tooling | **None** (no Capacitor / Expo / React Native in `package.json`) | Green field — nothing to unwind |

The server dependency (server components / server actions) is the single most important architectural
fact: it steers us to the *remote/hybrid* load model below, not a static export.

## Why Capacitor (vs the alternatives)

| Path | Effort | Native APIs (BLE/camera/push) | Store presence | Code reuse | Verdict |
|------|--------|-------------------------------|----------------|-----------|---------|
| **Installable PWA only** | ~free | ✗ on iOS (no Web Bluetooth) | ✗ | 100% | Do now; insufficient for the laser |
| **Capacitor shell** | Weeks | ✓ (native plugins) | ✓ App Store + Play | ~100% | **Recommended** |
| **React Native / native rewrite** | Months | ✓ | ✓ | UI rewritten; only logic/types shareable | Avoid — prohibitive, dual codebase forever |

Capacitor (by Ionic) wraps the existing web app in a native WebView (WKWebView on iOS, Android
WebView) and exposes native device APIs through a JS bridge. The web codebase is reused essentially
wholesale.

## The core architectural decision — how the shell loads the app

Next.js is server-driven, so this is **the** decision:

- **Model A — remote/hybrid (RECOMMENDED).** `capacitor.config.ts` sets `server.url` to the hosted
  Vercel app; the WebView loads the live app. **Server components and server actions keep working
  unchanged.** Native plugins are available through the Capacitor bridge. Offline is handled by the
  existing service worker + sync engine. *Smallest change, lowest risk.* Trade-offs: first load needs
  network; session cookies must persist in the WebView (verify); Apple "minimum functionality" review
  (mitigated by shipping real native features — see Risks).
- **Model B — static export + client API.** `next export` to static assets bundled in the app. This
  **fights the current architecture** — server components and server actions would have to be
  re-architected into client-side calls to API routes. Large, invasive, and throws away the SSR
  model. *Not recommended.*

**Verdict: Model A.** It preserves the entire current app and its data model; the native shell exists
only to host the WebView and carry the native bridges.

## What actually changes in the codebase (small, additive)

| Change | Files / packages | Note |
|--------|------------------|------|
| Add Capacitor | `@capacitor/core`, `@capacitor/cli`, `@capacitor/ios`, `@capacitor/android`; `capacitor.config.ts` | `server.url` → hosted app (Model A) |
| Native projects | new `ios/` (Xcode) and `android/` (Android Studio) directories | generated by `npx cap add ios/android` |
| Bluetooth bridge | `@capacitor-community/bluetooth-le` | the plugin that gives **iOS** the BLE the web can't — powers #30 |
| Runtime detection | small helper, e.g. `src/lib/platform.ts` (`Capacitor.isNativePlatform()`) | show the "Connect laser" affordance only where BLE exists; web stays unchanged |
| App identity | icons + splash (reuse `icon.svg`), app id, deep-link / URL scheme | so the app opens the right routes |

Everything else — routes, stores, server actions, UI, offline sync — is untouched.

## Phased rollout (sequenced with #30)

- **Phase 0 — tighten the PWA (now, ~free).** Confirm the manifest is clean and the app is genuinely
  installable (home-screen icon, offline). Ships the "feels like an app" win immediately, no store, no
  wrapper. *Independent of everything below.*
- **Phase 1 — stand up the Capacitor shell.** Add Capacitor (Model A), generate iOS + Android
  projects, get both building and loading the hosted app on a real device / TestFlight / Play internal
  testing. **No feature change** — this phase only proves the wrapper works end to end.
- **Phase 2 — Bluetooth + the laser (#30).** Add `@capacitor-community/bluetooth-le`, build the
  quick-measure connect-and-fill flow behind platform detection. **This is the payoff** and the reason
  to wrap at all. (The manual quick-measure UI from #30 can ship earlier on web; this phase adds the
  live laser on native.)
- **Phase 3 — store release.** Apple + Google enrollment, submission, review, public listing. Layer in
  push / camera later if wanted.

shells + two store listings), not money.

## Risks & mitigations

- **Apple 4.2 "minimum functionality" (just-a-website) rejection.** Mitigation: submit *with* real
  native features (BLE laser, camera). Genuine device integration clears the bar; that is exactly what
  Phase 2 delivers — so submit after Phase 2, not after Phase 1.
- **Server dependency in the field.** Server-rendered routes need connectivity on first load; the
  existing sync engine covers data but not initial SSR. Decide which routes must work fully offline and
  confirm the service worker caches them.
- **Session cookies inside the WebView.** Auth relies on cookies; verify they persist in the Capacitor
  WKWebView across launches (may need `server` / cookie config).
- **Capacitor ↔ Next 16 App Router.** The `server.url` model sidesteps most build-time coupling; still
  confirm current compatibility before Phase 1.
- **Maintenance doubles.** Accept knowingly — this is the real recurring cost.
